# 输入法市场调研（2026-11-19）

调研目的：给 Clavis 自研输入法的**三条待定设计**找外部依据——候选窗视觉、跨平台词库、本地模型。
所有事实标注来源；无法核实的写 `未验证`。

## 0. 结论先放

| 议题 | 市场结论 | 对 Clavis 的处置 |
|---|---|---|
| 候选窗视觉 | 微信输入法靠「极简、顶栏不塞入口、无广告」拿下口碑；搜狗 2025 被用户批量卸载的抱怨集中在**常用字不在首页、要翻页**、**纠正过的词不记住** | 我们的 A1（整句进首页）方向对；A5（四级层次）比堆功能更对路。**不要往候选窗加功能入口** |
| 跨平台词库 | Rime 系的答案是「共享目录各写一份 userdb」，不是合并成单一文件；且**只同步用户词库，不同步词库定义** | 我们的 B4 合并函数要做，但分发形态学 Rime：每设备一份、合并发生在加载期而非文件层 |
| 本地模型 | 讯飞已训端侧大模型做组句与下一句联想；业内判断「端侧与隐私从加分项变成硬门槛」 | 在线逐键推理不现实（延迟），但**端侧做批量挖掘**是主流做法；隐私叙事要写进产品 |

## 1. 候选窗：市场怎么做的

### 1.1 用户真正的抱怨是什么

知乎《输入法"变笨"了吗？》（2025 末）记录了一个典型：一位用搜狗 17 年的文字工作者卸载了它，原因是

- 想打「是」，频繁推「事」，**且「事」通常不在首页候选**，要翻页才能找到常见字
- 「呀」被误判成「压」「亚」，**即便多次纠正也没记住**

这条对我们是双重的：

1. **A1 的判断被外部验证了**——「答案不在首页」是会让人卸载输入法的量级问题。我们把整句候选提到首页第 2 位，方向正确。
2. **用户词频学习是核心资产**——「纠正了却不记住」是头部厂商都在挨骂的点。我们的 `ime_user_lexicon` + `rankTierByUserBoost` 已经在做，但跨设备不同步（见 §2）会让这个优势在第二台机器上归零。

来源：<https://zhuanlan.zhihu.com/p/1993647228984788901>

### 1.2 视觉风格：极简是共识

微信输入法被反复称道的是「简洁的 UI，不像一些输入法在顶栏塞满各种按键和功能入口，还会跳广告横幅」（钛媒体）。

对我们直接的含义：

- 候选窗**只做候选**，不加设置入口、主题入口、皮肤推荐
- 浮层要克制：一处强调色、一条发丝线、一个选中态，够了
- 我们已经去掉的 3D 数字键帽 + 弹簧动画，方向与市场一致

来源：<https://www.tmtpost.com/6353070.html>

### 1.3 我们与头部的真实差距（不粉饰）

| 维度 | 头部（搜狗/微信/讯飞） | Clavis 现状 |
|---|---|---|
| 组句语言模型 | 云端 + 端侧大模型，长句准确率高 | 无语言模型，靠词典最大匹配拼句；「也数根」这类组合质量差 |
| 用户习惯学习 | 云端跨设备 | 本地 SQLite，单机有效 |
| 候选排序 | 多特征（上下文、频率、时间） | 词频 + bigram 两档，`prevWord` 单一来源 |
| 长句输入 | 整句一次上屏 | 逐段选，需多次按键 |

**结论**：Clavis 输入法在「准确率」上短期不可能追平头部，**不该朝那个方向竞争**。它的位置是「键盘优先 + 本地优先 + 可编程」的窄场景工具，打的是隐私与可控，不是输入法整体替代。

## 2. 跨平台词库：Rime 的解法

Rime 系（鼠鬚管/Squirrel）的多设备同步机制（薄荷输入法文档 + squirrel#858）：

1. 配置目录下的 `installation.yaml` 存 `installation_id`（默认 UUID，可自定义成 `Macbook-M2Max` 这种可读名）
2. 用户追加 `sync_dir`，指向 iCloud/Dropbox/OneDrive 的共享目录
3. 执行同步后，**每台设备在共享目录下生成自己的 `<installation_id>.userdb.txt`**
4. 只有根目录的 YAML/TXT 被单向备份，**`dicts/` 子目录里的词库与 lua 脚本不同步**

来源：<https://www.mintimate.cc/zh/guide/deviceSync.html>、<https://github.com/rime/squirrel/issues/858>

### 2.1 从中学到什么

| 观察 | 我们的处置 |
|---|---|
| 同步单元是「每设备一份 userdb」，不是单一合并文件 | B4 的 `MergeLearning(a,b)` 仍要写，但**用于加载期合并**，磁盘上各设备保留自己的快照 |
| 只同步用户词库，不同步词库定义 | 我们的 starter 走版本化产物内嵌（B1 已做），用户词库走 SQLite + 导出（B2），两者分离——一致 |
| `installation_id` 可读化 | 我们的设备标识也该允许命名（`mini` / `windows`），否则用户看不懂哪份是谁的 |
| 有「数据孤岛」痛点（本地词库不通） | 这正是我们的机会：Clavis 已有 sync 协议骨架（虽然密码学待修），比 Rime 的手工目录更可控 |

**关键判断**：不做「合并成一个全局词库文件」。理由：两设备同时写一个共享文件必然冲突，Rime 十五年经验就是各写各的。合并发生在**读取时**，写入永远本设备独占。

### 2.2 一个 Rime 没做而我们能做的

Rime 的 userdb 是二进制的，用户无法审计「我到底学了哪些词」。我们可以：

- 导出为 Rime `.dict.yaml`（B2 已规划），人可读、可编辑、可 diff
- 合并时给出**来源标注**（这个词来自 mini 还是 windows），设置页可见

## 3. 本地模型：市场的真实位置

### 3.1 事实

- **讯飞**：基于星火训练了**端侧大模型**，用于输入过程、上屏、以及「下一句话如何联想」（53AI，2024-10）
- **行业判断**：腾讯云技术社区《大模型下场做输入法》明确写「端侧与隐私从加分项变成硬门槛。输入法经过的是最高敏感的数据流。谁能把改写/校对/部分推理放在端上，谁就更容易赢得默认信任」
- **端侧小模型**：MiniCPM 系列主打端侧算力与内存效率

来源：<https://www.53ai.com/news/LargeLanguageModel/2024102879132.html>、<https://developer.cloud.tencent.com/article/2602610>、<https://modelbest.cn/>

### 3.2 对我们的含义

**在线逐键推理是死路**，这一点市场数据反过来验证了：讯飞是把端侧模型**专门为输入场景训练**并做进产品，不是拿通用小模型逐键问。我们的约束更硬：

- `AITimeout = 1.5s`（现有），本地模型冷启动 5–20s，必然超时
- 输入法钩子线程不能等 I/O

所以 C 线的定位调整为（与方案一致，但依据更硬）：

| 路径 | 定位 | 依据 |
|---|---|---|
| 离线批量挖掘（C2） | **主路径**：从剪贴板/历史文本挖词组写进用户词库 | 讯飞的端侧模型也是做「联想补全」这类批量任务，不是逐键 |
| 在线 ✦ 候选（C3） | 次路径，仅当本地模型已预热 | 1.5s 硬超时决定它只能当锦上添花 |
| 逐键本地推理 | **不做** | 延迟物理上不可行 |

### 3.3 隐私叙事

腾讯云那篇的判断值得直接借用：输入法流经的是最高敏感数据。Clavis 的差异化点不是「更准」，而是：

- 词库、学习数据、剪贴板全在本地
- 可选同步走端到端加密（sync 协议已设计，S1 待修密码学）
- 本地模型只读本机文本，不出机器

这三条写进 README 的定位段，比列功能有说服力。

## 4. 对现有方案的修订

| 编号 | 原方案 | 修订 |
|---|---|---|
| B4 | 「多设备合并用 frequency 求和，不做 LWW」 | **加强**：合并只在读取期发生；磁盘上每设备保留自份（学 Rime）；并给来源标注 |
| B5 | 缓存键加 compilerVersion | 不变 |
| C2 | 离线挖掘 | **加强**：明确「这是主路径」，并写清为什么不学头部做逐键推理 |
| A1 | 整句候选进首页 | 不变，但依据从「我的判断」升级为「用户会因此卸载输入法」 |
| 新增 | — | 候选窗**不加任何功能入口**（设置/主题/皮肤），这条写进设计约束 |

## 5. 明确不做（依据市场）

- 不做云输入法（与隐私定位冲突，且头部已卷到 84.4% 市占）
- 不做逐键本地大模型推理（延迟不可行，讯飞也是专门训练端侧小模型而非通用模型）
- 不做词库市场/皮肤商城（微信输入法的教训是「少即是多」）
- 不追长句准确率（短期不可能追平，应该承认）
